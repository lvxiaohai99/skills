# 软件概要设计报告 — 默认章节骨架

仅当用户 Word 模板文件名/标题含「概要设计」，或**没有 Word、只要 Markdown** 时使用。其它模板以 `inspect_template.py` 的 Heading 为准，不要硬套本章名。

本骨架相对《软件详细设计报告》V1.0.2：**没有** 2.3 复杂函数流程图、**没有** 2.4 七行函数表。那些属于详设。

## 版式（有 Word 模板时）

与详设相同：克隆模板，保留 sectPr / 页眉页脚 / Heading 编号。见 [docx-ooxml.md](docx-ooxml.md)。封面标题改为「…软件概要设计报告_…模块」。

## 正式稿禁止写入

【模板说明】【示例】必须删除。

## 章节骨架

1 概述
- 1.1 目的 — 「本文档描述了…软件_…模块的概要设计，用于指导详细设计与开发。」含适用人员。
- 1.2 范围 — 本模块做/不做；与邻模块边界一句话
- 1.3 参考文件 — `（1）《…》`，与仓库架构/需求文档名称一致
- 1.4 缩略语 — 先一句再三列表：序号 | 缩略语 | 含义

2 总体设计
- 2.1 设计约束与假设 — 平台、语言、配置字、存储介质；代码没有的标假设
- 2.2 系统上下文与边界 — 文字 + 边界图（红本模块 / 黄内部 / 灰外部）；名称与架构文档字面一致
  - 2.2.1 输入 — 按外部模块写本模块需要什么
  - 2.2.2 输出 — 本模块向外提供什么
- 2.3 逻辑架构 — 分层/进程/域，配架构图
- 2.4 运行视图 — 谁先启动、App 杀掉是否还在、下电是否丢状态；代码未体现则写「代码未表明」不要编

3 模块设计
- 3.1 模块划分与依赖 — 开篇「X模块分为 N 个单元：…」。依赖图按被依赖者在上。给出建议开发顺序 1…N。
- 3.2 起每个内部模块一节：
  - 职责
  - 覆盖的需求 ID（有功能需求表才写）
  - 对外接口概要（名称、方向、关键字段、错误；不是函数表）
  - 关键数据
  - 失败与降级

4 接口设计概要

表：接口 | 方向 | 关键字段/语义 | 对应模块 | 备注（OPEN 标未在代码出现的）

5 数据设计概要

实体 | 关键属性 | 来源与去向 | 清理/留存。不写完整 DDL，除非代码里已有 schema 文件。

6 关键动态行为

P0 主路径时序图一张；代码里第二条关键路径再一张。有明确状态枚举则补状态图。图后用①②文字对应时序，不要展开到函数实现。

7 非功能设计

把可靠性/时延/存储/安全落到具体模块（队列、优先级、超时），不要只复述指标。代码没有的手段不要写。

8 追溯

| 需求或能力 | 模块 | 流程/接口 | 备注 |
代码有、需求没有：仍写模块，备注「代码存在、需求未列」。需求有、代码没有：不画进架构，只在本表标缺口。

9 遗留问题（留给详细设计）

函数级算法、圈复杂度流程、完整字段表、未锁定的协议细节。

## 边界图配色

- 红色框 = 本模块
- 黄色框 = 模块内单元
- 灰色框 = 外部关联模块
