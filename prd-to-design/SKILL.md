# PRD → 功能需求表 → 概要设计

把产品侧 PRD 翻译成研发可执行的两份文档。**章节结构以选定模板为准**，拆需求规则以本文件 + [references/reference.md](references/reference.md) 为准。

1. **功能需求表**：可编号、可验收、可追溯（研发视角，不是 PRD 摘抄）。
2. **概要设计**：按**开发依赖顺序**组织，每个设计点回指功能 ID。

`$SKILL_DIR` = 本 skill 根目录。模板清单见 [templates/catalog.md](templates/catalog.md)；质量样例见 [references/examples.md](references/examples.md)。

## 何时启用

用户给出 PRD，或要功能需求表 / 概要设计 / HLD / 指定模板套用。

## 选定模板

在抽 PRD 之前先定模板。写两份文档前 **Read 选中的模板全文**，按其中标题填，不要凭记忆用旧骨架。

**优先级（高 → 低）：**

1. 用户分别给出了「功能需求模板」「概要设计模板」两个文件路径。
2. 用户给了一个目录，且其中有 `功能需求.md` 与 `概要设计.md`（文件名也可是 `fr.md` / `hld.md`）。
3. 用户说了内置包名或别名 → 用 `$SKILL_DIR/templates/<包名>/`。包名与别名见 catalog。
4. 都没有 → `templates/default/`。

只指定了其中一份时，另一份用 `default` 里对应文件。

用户给的自定义模板：

- 保留其全部标题；不要改回 default 的章节名。
- 若模板没有「待确认 / 追溯 / 范围外」而内容需要，**文末补一节**并注明「模板未含此节，已补」。
- 模板里的 HTML 注释是填写规则，落盘成品里删掉。
- `{{占位符}}` 换成实值。

内置包：

| 用户可能说的 | 目录 |
| --- | --- |
| 不说 / 通用 / 默认 | `templates/default/` |
| 车载、座舱、车机、IVI、DVR | `templates/ivi/` |

自建包：在 `templates/<新名字>/` 放下两个 md，并在 catalog 加一行。或把模板放项目里用路径指定，不必改 skill。

对话摘要里写清本次用的模板路径。

## 工作流程

```
任务进度:
- [ ] 0. 选定模板并读入两份骨架
- [ ] 1. 拿到完整 PRD 文本
- [ ] 2. 消化：目标 / 角色 / 范围 / 约束 / 待确认
- [ ] 3. 按功能需求模板输出并保存
- [ ] 4. 按概要设计模板、基于功能需求表输出并保存
- [ ] 5. 对话里给目录、所用模板、待确认、风险摘要
```

即使用户只要概要设计，也必须先落盘功能需求表。

### 1. 读取 PRD

支持：`.pdf` `.docx` `.doc` `.pptx` `.ppt` `.xlsx` `.xls` `.md` `.markdown` `.txt` `.html` `.htm` `.csv`

**有文件路径时**先跑提取脚本，不要猜二进制：

```bash
python3 -m venv "$SKILL_DIR/.venv"
"$SKILL_DIR/.venv/bin/pip" install -r "$SKILL_DIR/requirements.txt"

PYTHONIOENCODING=utf-8 python3 "$SKILL_DIR/scripts/extract_prd.py" "<PRD路径>" ["<附件2>"]
```

已有 venv 可直接跑 `extract_prd.py`。读写 UTF-8。打印 `===PRD_META===` / `===PRD_TEXT===`。

- `chars < 200` 或 `low_text`：扫描件、以图为主的 PPT。请用户改发 Word/Markdown。架构图不要臆造，可建议 `image-to-editable-diagram`。
- 旧版 `.doc` / `.ppt` 需要 LibreOffice；否则请另存为 `.docx` / `.pptx`。
- 粘贴正文：跳过脚本。多份材料一次传入，来源列区分文件。
- 没路径：在 cwd 的 `PRD/`、`docs/`、`需求/` 找；找不到再问。
- Excel 已是需求清单：把列名归一到**当前功能需求模板的表头**，缺列补「PRD 未写」或 OPEN。

### 2. 消化 PRD

只根据原文。分类进阅读摘要（或模板里的等价节）：

| 类别 | 放什么 |
|---|---|
| 目标与成功标准 | 要解决什么、如何算做成 |
| 角色与场景 | 谁、触发、得到什么 |
| 范围内 / 范围外 | 明确不做的也留下 |
| 约束 | 平台、协议、法规、性能、安全 |
| 非功能 | 可靠性、时延、弱网、功耗、可运维 |
| 待确认 | 含糊、矛盾、缺接口/状态机 |

产品形容词落不成可测行为 → OPEN，不要当已定功能。

`ivi` 包还要核：上电时序、配置字、存储介质、摄像/车身信号是否给了报文。

### 3. 功能需求表（面向研发）

按**选定的功能需求模板**填。规则不变：

- ID：`FR-模块-序号`；非功能 `NFR-`；约束 `CST-`；待确认 `OPEN-`。概要设计只引用这些 ID。
- 一条 ID = 一个可独立验收的能力。
- 优先级：P0 无则不能发布；P1 完整体验；P2 增强。PRD 没标则推断并注明。
- FR / NFR / OPEN 不要混成一类。
- 推导项必须标 `来源：推导` 并挂既有 ID。
- 验收：`给定…当…则…`。禁止「体验良好」。

细则见 [references/reference.md](references/reference.md)。

### 4. 概要设计（符合开发逻辑）

只依据已定稿的功能需求表。按**选定的概要设计模板**填。

1. 先边界再模块，按实现依赖写，不按 PRD 目录。
2. 被依赖的模块在前。
3. 每模块：职责、覆盖的 ID、接口、失败怎么处理。
4. P0 主路径时序；异常单独写。
5. 停在概要层，不要写成详细设计。
6. 技术栈：PRD 或现有仓库已有则跟随；否则写假设。
7. OPEN 给可选方案，标「待确认后锁定」。

### 5. 输出与保存

聊天里给：所用模板、产物路径、FR/NFR/OPEN 数量、P0、先做的模块、阻塞编码的 OPEN。

落盘 UTF-8 Markdown：

| 文档 | 文件名 |
|---|---|
| 功能需求表 | `<主名>-功能需求.md` |
| 概要设计 | `<主名>-概要设计.md` |

| 优先级 | 保存位置 |
|---|---|
| 用户指定了目录 | 按用户指定 |
| 正在测 `test/prd-to-design/` | `test/prd-to-design/outputs/` |
| 其它 | cwd 下 `设计/<主名>/` |

`<主名>` = PRD 主文件名去扩展名。已有同名则覆盖。

## 约束

- 简体中文。指定了模板就必须用该骨架。
- 功能需求表与概要设计双向可追溯；禁止设计里偷加功能（推导须标记）。
- 禁止把 OPEN 写成已定实现。
- PRD 矛盾列入 OPEN 并置顶。
- 自检见 [references/reference.md](references/reference.md) 末尾；另加：成品标题与选定模板一致。
