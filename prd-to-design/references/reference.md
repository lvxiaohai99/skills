# 拆需求与概要设计细则

只在写功能需求表或概要设计时阅读。SKILL.md 的模板与流程优先。

## 从 PRD 句子到 FR 的拆法

把产品描述变成「系统在什么条件下必须做什么，怎样算对」。

| PRD 原文倾向 | 处理 |
|---|---|
| 「用户可以上传日志」 | 拆：触发入口、打包、鉴权、传输、进度、成功/失败反馈，能独立测的就独立编号 |
| 「支持弱网」 | 升为 NFR，并推导 FR：重试、断点、队列、超时提示 |
| 「体验流畅」 | 无指标则 OPEN；有「进度 500ms 内出现」则写成 NFR 或 FR 验收 |
| 「等」/「后续再定」/「视情况」 | OPEN，不要写成 P2 假装已定 |
| 同一件事在两章写法不同 | OPEN，列出冲突原文 |
| 已经是表格（Excel） | 映射列：名称→功能名称，描述→简述/主流程，优先级保持或换算 P0/P1/P2 |

**一条 FR 的边界**：换一个失败原因或换一个角色仍是同一能力 → 仍是一条，写进「异常」。换模块或换验收对象 → 新 ID。

**不要拆过细**：按钮文案、像素间距除非是合规/品牌硬性要求，否则不进 FR。

## 优先级

| 级 | 含义 | 典型 |
|---|---|---|
| P0 | 没有则主闭环不成立，或安全/合规/行车安全 | 采集、上传成功、失败可感知、隐私脱敏 |
| P1 | 完整体验、可运维 | 进度、历史列表、手动重试 |
| P2 | 增强 | 批量、高级筛选、导出 |

PRD 标了「高/中/低」或「Must/Should/Could」时换算并在备注保留原文用语。

## 验收标准

每条至少一条能被测试写成 Pass/Fail 的句子。优先：

`给定 [前置]，当 [动作]，则 [可观察结果]（含超时/错误码/落盘位置）。`

反例：「系统应稳定上传」「用户体验好」。

能量化的写数字（大小上限、重试次数、超时）。PRD 没数字时：写 OPEN，或标「推导」并给建议默认（如重试 3 次、指数退避），供评审拍板。

## 来源列

- `PRD §x / 原文关键词`：能指回章节或表格行
- `附件: 文件名`
- `推导，依据 FR-… / NFR-…`：研发惯例补全，评审可砍
- 不要写「常识」「业界实践」而不挂 ID

## 概要设计怎么才算「符合开发逻辑」

错误组织（按 PRD 目录）：背景故事 → 用户价值 → 全部 UI → 最后才提存储。

正确组织（按实现依赖）：

1. 上下文与边界（跟谁说话、不碰谁）
2. 存储与任务模型（队列、文件、状态）
3. 领域模块（采集、脱敏、传输）
4. 对外接口 / HMI
5. 把 P0 串成一条可跑通的时序
6. NFR 落到具体模块（不要另起一篇空话）

模块顺序检验：如果砍掉后面的模块，前面的模块仍能单测或用桩跑通，顺序就对了。

## 深度控制

| 要写 | 不要写（除非 PRD 已规定） |
|---|---|
| 模块职责、依赖方向 | 类图到每个 getter |
| 接口名、关键字段、错误语义 | 完整 protobuf/JSON schema 小说 |
| 实体与关键属性、留存策略 | 全量 DDL、索引调优论文 |
| 状态机主状态 | 每个 UI 控件回调 |
| 线程/进程/是否可重入 一句话 | 无根据的微服务拆分 |

嵌入式 / 车载场景额外想一层：生命周期（点火、休眠、掉电）、存储分区、不要阻塞关键任务。PRD 没写也要在 OPEN 或推导里点出来。

## 技术栈假设

1. PRD 或现有仓库已有栈 → 跟随，并在文档信息写「跟随现有」
2. 都没有 → 列 3～5 条假设（语言、存储、传输、部署），各一行理由
3. 禁止借题发挥引入 PRD 未要求的消息中间件、服务网格、大数据平台

## 模板

产出章节以 `$SKILL_DIR/templates/` 下选定包为准，不在本文件重复骨架。

- 未指定 → `default`
- 车机/座舱且用户指定了 `ivi`（或别名）→ `ivi`（多「车载专项核对」和运行域）
- 用户路径 → 原样用，缺节才文末补

拆条、优先级、验收写法不随模板变。
