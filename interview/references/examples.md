## 一面题（合格）

### Q1. 订单峰值从 200 提到 2000，Redis 在链路里承担什么？如果缓存穿透和击穿同时出现，你当时怎么处理？

- **考察点：** 缓存角色、穿透/击穿、是否亲历
- **简历锚点：** 某零售订单服务，「Redis 削峰 / QPS 200→2000」
- **期望要点：**
  - 能说明 Redis 在读多写少链路上的角色（热点缓存 / 削峰）
  - 能区分穿透 vs 击穿
  - 能说出至少一种真实应对（空值、互斥、逻辑过期、限流等）
  - 能提到如何观察命中率或 DB 压力
- **参考答案：**
  （对照用，非候选人原话）
  1. **角色：** 订单查询热点放 Redis，挡住重复读；写路径仍以 DB 为准，缓存做失效或短 TTL，避免当唯一真相。
  2. **穿透：** 查询不存在的订单号打穿到 DB → 缓存空值（短 TTL）或布隆过滤拦截非法 ID。
  3. **击穿：** 热点 key 过期瞬间并发打 DB → 互斥重建（单飞）、逻辑过期、或永不过期+异步刷新中的一种。
  4. **结合其简历：** QPS 200→2000 时，应能说明主要收益来自读缓存命中，而不是只改了线程池；应能描述当时如何看 Redis 命中率与 MySQL QPS。
  5. **简历未写的数字：** 不要求背出精确命中率，但应能给出测量方法与大致量级。
- **评分口径：**
  - **过线：** 分清穿透/击穿，并能说出一种可行手段 + 与订单读路径的关系
  - **加分：** 有监控指标、回滚策略，或讲清与 DB 一致性的取舍
  - **疑点：** 只会背名词；坚持「全走 Redis 无 DB」；说不出自己项目里具体放了什么 key
- **追问：** 当时 MySQL 的 QPS 和 Redis 命中率大概是多少？
- **追问参考：** 过线应给出量级或承认当时没记但说明怎么查（监控面板/慢查询）；完全拒绝谈数字且无测量方法 → 疑点。

## 二面题（合格）

### Q1. 若明年大促目标是 1 万 QPS，现有 Spring Boot 单体订单服务，你会按什么顺序拆，哪些先不拆？

- **考察点：** 拆分边界、数据一致性、容量规划
- **简历锚点：** 订单服务仍偏单体，已做 Redis 与 SQL 优化
- **期望要点：**
  - 按瓶颈拆，不为拆而拆
  - 提到数据一致性 / 幂等 / 回滚中的至少两项
  - 承认简历未覆盖 K8s 时的补齐思路
- **参考答案：**
  （对照用，非候选人原话）
  1. **先量再建：** 用压测确认瓶颈在查询、下单写库、还是库存；先垂直扩容与 SQL/缓存极致优化，再拆。
  2. **建议拆分顺序举例：** 读多的订单查询 → 库存扣减 → 支付回调；核心下单事务先留单体或小步抽库。
  3. **一致性：** 跨服务用本地消息表 / Outbox 或准实时对账；强调幂等键与失败可补偿。
  4. **先不拆：** 管理后台、低频配置、强一致小事务。
  5. **结合其简历：** 已有 Redis 与 QPS 提升经验，应先说明 2000→10000 还差在哪，而不是直接上微服务名词；K8s 未写则应说容器编排可后置，先把服务边界与数据边界想清。
- **评分口径：**
  - **过线：** 有拆分顺序与「先不拆」清单，并提到一致性手段之一
  - **加分：** 给出容量粗算、回滚预案、或与组织协作方式
  - **疑点：** 一上来全拆成十几微服务；否认一致性问题；虚构已上 K8s
- **追问：** 拆分后一次下单跨多个服务，你用本地消息表还是 TCC，为什么？
- **追问参考：** 过线能说清各自适用场景（消息表更常见于最终一致订单流；TCC 成本高）；说「都行」但不给标准 → 弱。
